# License Lens — 可恢复的扫描台账

锁文件不再「盖」到同一份清单上。每个锁文件导入后形成**独立批次**，包按
**内容指纹**识别，人工裁决与指纹绑定，解析/分析整批原子提交、失败可重试且
已确认结果不丢。

## 数据模型（`src/ledger/`）

| 概念 | 说明 |
|---|---|
| 批次 `Batch` | 一个锁文件 = 一个批次（`ord` 递增、独立 `packages`、独立状态）。两个窗口/两次提交永远是两个批次，不会混成一批。 |
| 内容指纹 `fp` | `生态 + 包名 + 版本 + 许可证` 的 FNV-1a 哈希（`codec.ts`）。任一变化即新指纹。 |
| 人工裁决 `decisions[fp]` | 裁决挂在指纹上而不是批次上，并快照裁决时的 `source`。指纹不变 → 跨批次、重试后照旧可用；指纹一变 → 查不到，包自动回「待复核」。 |
| 分析缓存 `analysis[fp]` | 机器初判也按指纹缓存，是失败重试时「已确认结果照旧可用」的基础。 |

### 批次状态机

```
导入 ──parse OK──▶ parsing ──全部指纹分析成功──▶ ready   （唯一可进入发布清单）
  │                   │
  └─parse 失败──▶ failed ◀─任一指纹分析失败/中断──┘
                   │ 重试（重新解析 + 复用缓存，只补跑缺失指纹）
                   └▶ parsing
```

- **原子性**：`settleBatch` 校验所有指纹都有结果才置 `ready`，否则整批 `failed`，
  绝不会有半成品包出现在发布清单里（`engine.ts`）。
- **可恢复**：批次含原始锁文件内容；刷新后 `parsing` 批次自动续跑（`useLedger.ts`）。
- 分析中途失败时，已完成的指纹结果保留在全局缓存；重试只补齐剩余部分。

### 发布清单

`releaseManifest()` 对每个生态只取 `ord` 最大的 **ready** 批次；失败批次不会
顶替掉上一个有效批次。发布清单中只呈现当前有效裁决（approved / rejected /
pending），并可导出 Markdown。

### 批次比较

`diffBatches(base, target)` 按内容指纹输出：

- **新增**：target 有、base 无的指纹；
- **消失**：base 有、target 无的指纹；
- **裁决变化**：同名包指纹变了（版本或许可证被改），旧裁决失效、`from → pending`。

## 支持的锁文件

`package-lock.json`（v1/v2/v3）、`yarn.lock`（v1）、`composer.lock`。

## 演练场景（导入弹窗）

1. 两个窗口同时提交 —— npm + composer 两个批次并行解析；
2. 分析中断 → 重试 —— 整批回滚后重试，复用已确认指纹结果；
3. 导入破损锁文件 —— parse 即失败、空行，可重试；
4. 新锁文件盖旧清单 —— v1→v2，观察同指纹裁决保留、变化指纹回待复核，
   并用「批次比较」查看新增/消失/裁决变化。
